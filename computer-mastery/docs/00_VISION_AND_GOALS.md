# Vision and Goals

## Long-Term Vision

Build a homeschool-style computer science and computer engineering education with the seriousness, depth, and rigor associated with an elite technical program.

The goal is not credential imitation. The goal is capability.

The desired end state is an engineer who can understand, instrument, modify, defend, automate, and reshape computer systems — and who habitually builds tools and environments that create unusual leverage.

Over time, this program should produce comfort across multiple layers of the machine:

```text
Application Code
      ↓
Libraries / Runtime
      ↓
Compiler / Linker / ABI
      ↓
Executable / Binary Format
      ↓
Process / Threads / Memory
      ↓
Operating System
      ↓
Networking / Storage / Devices
      ↓
CPU / Architecture
      ↓
Hardware
```

Security crosses every layer.

Toolsmithing crosses every layer.

## North Star

> Become the kind of engineer who can sit down at an unfamiliar computer problem, discover what is actually happening, and manufacture whatever leverage is needed to solve it.

The desired reaction to a mysterious system is:

> I do not know the answer yet, but I know how to find out.

And when the existing tools are insufficient:

> I can build what I need.

## Desired Engineering Identity

The curriculum should deliberately develop several overlapping identities.

### Investigator

Can enter an unfamiliar system, gather evidence, form hypotheses, design experiments, and discover the truth.

### Toolsmith

Can turn repeated work, missing visibility, and awkward workflows into reusable tools, scripts, services, libraries, and automation.

### Environment Engineer

Gradually shapes the computer around personal workflows rather than accepting every default interface or process.

### Defender

Understands attack surfaces, trust boundaries, suspicious behavior, integrity, telemetry, and incident investigation well enough to build meaningful defensive visibility.

### Technical Inventor

Can combine familiar primitives in unfamiliar ways, recognize problems before a specification exists, and design systems that were not handed down by a tutorial.

### Evidence Engineer

Does not confuse plausible explanations with proven explanations. Can design tests, benchmarks, instrumentation, traces, profilers, visualizations, and controlled experiments that turn claims into evidence.

### Adaptive Engineer

Continuously updates skills against the current state of computing and security without abandoning durable fundamentals or chasing hype.

## Professional Goal

Become unusually capable at difficult engineering work, especially problems that cross abstraction boundaries.

Examples include platform-specific crashes, memory corruption, deadlocks and race conditions, engine or SDK integration failures, performance problems, networking failures, build and linker issues, binary inspection, process and OS behavior, incident investigation, defensive security, remote diagnostics, machine comparison, and custom internal tooling.

The goal is not prestige or employment at a particular organization. The goal is to become exceptionally good at the work itself.

## Personal Computing Goal

Over years, build and refine a personal computing system that reflects accumulated knowledge and repeated real-world needs.

This may eventually include custom shell behavior, developer commands, build diagnostics, machine inventory, remote administration, observability, security monitoring, environment validation, automation, reusable libraries, and other tools that emerge naturally.

Do not rebuild mature software merely for ego or novelty. Use strong existing tools when they are the right answer. Build custom layers where doing so creates genuine understanding, visibility, integration, control, or leverage.

## Intellectual Goal

Develop enough breadth to understand the major fields of computer science and computer engineering and enough depth to become an authority in selected areas.

Authority is a multi-year path. It eventually requires textbooks, primary documentation, source code, academic papers, reproducing experiments, contributing tools or research, questioning accepted assumptions, and specializing deeply.

## What Success Looks Like

Success is not measured by the number of topics completed.

Success increasingly looks like:

- unfamiliar systems becoming less intimidating
- evidence replacing guesses
- claims of improvement being backed by repeatable tests, measurements, and profiles
- repeated work becoming automated
- personal tools becoming genuinely useful
- earlier tools being extended rather than abandoned
- multiple disciplines being combined naturally
- security questions becoming habitual
- real incidents becoming learning opportunities
- the student defining problems and inventing solutions without being told what to build
- the student being able to absorb important new computing paradigms without becoming dependent on them

## What This Curriculum Is Not

This is not a LeetCode-only program, a tutorial playlist, a sequence of toy syntax exercises, a collection of disconnected security tricks, an AI-generated-code curriculum, a catalog of flashy hacker tricks, or a race to finish topics.

Depth matters more than speed.

Capability matters more than appearance.
